# Rye Development Guide

Rye is a Bun + TypeScript monorepo managed with Turborepo.

## Workspace Layout

- `packages/agent-core/` — Backend Hono HTTP/SSE server (port `7337`), `pi-ai` agent loop, tool registry, SQLite/JSON stores, decision model router, MCP client, and embeddings/RAG engine.
- `packages/shared/` — Shared TypeScript types (`SSEEvent`, `PendingPrompt`, `SOP`, etc.) consumed by both `agent-core` and frontend apps.
- `apps/web/` — React 18 + Vite web UI (dev port `8080`, proxies API routes to `127.0.0.1:7337`).
- `apps/cli/` — Terminal CLI (`rye`) communicating with the agent-core server.

## Common Commands

```bash
bun install                                      # Install workspace dependencies
bun run dev                                      # Start agent-core + web + cli watchers via Turbo
bun run build                                    # Build all workspaces
bun run --cwd apps/web typecheck                 # Typecheck the React web app
bun run --cwd packages/agent-core build          # Bundle & verify agent-core
bun test packages/agent-core/tests               # Run agent-core unit tests (bun:test)
```

## Architecture & Conventions

### Backend (`packages/agent-core/src/`)

- **Entry & HTTP routes (`server.ts`)**: Hono app serving SSE streams (`POST /chat/`) and REST endpoints.
  - **Trailing slashes on sub-routers**: Mount sub-routers with a trailing slash (e.g. `app.route("/skill/", ...)`, `app.route("/agents/", ...)`, `app.route("/knowledge/", ...)`) so `r.get("/")` / `r.post("/")` answer at `/foo/` (matching `/sop/` and `/memory/`).
  - **Vite proxy parity**: Whenever you add a new top-level API route prefix in `server.ts`, add it to `server.proxy` in `apps/web/vite.config.ts` and never leave a compiled `apps/web/vite.config.js` beside it (Vite prefers `.js` over `.ts`). Proxy keys match as plain prefixes, so a prefix must not swallow a page address of the web app (`utils/routes.ts`): `/sop` is the regular expression `^/sop(?:/|\?|$)` so `/sops/<id>` stays a page, and `/memory` and `/agents`, which are both API prefixes and pages, answer a page load (`sec-fetch-mode: navigate` or `Accept: text/html`) of exactly that path with `index.html` (`pageLoad`). Check a new route prefix against those page addresses.
- **Agent Loop (`agent/loop.ts`)**:
  - Runs `knowledgeStore.searchForContext` and tool-group selection in parallel before building the prompt.
  - **Keep the system prompt stable between turns** so providers can reuse their cached prompt prefix and the Claude harness keeps its session. It may only change when the user changes something (environment, a saved memory, a new SOP). Anything that differs per turn (the time, knowledge notes found for this message, one-off results) goes in the `<rye_context>` block attached to the user message (`agent/turn-context.ts`), which is kept in history; use `stripTurnContext` wherever the user's typed text is needed.
  - Knowledge notes are attached only when they clearly match (`searchForContext`: standing out from the knowledge base's background similarity, or sharing enough keywords) and at most once per conversation. SOPs are not searched per turn; the prompt lists the full SOP index instead.
  - Supports custom `AgentDefinition` personas: injects agent instructions, pre-loads configured `tool_groups`, scopes `MemoryStore` + `KnowledgeStore`, and resolves inline `[[sop:id|title]]`, `[[skill:name]]`, and `[[knowledge:id|title]]` references pinned in agent instructions. The persona tells the model it is that agent, not Rye.
  - **Speakers.** Rye and agents can take turns in one session, so each reply is stamped with who wrote it: every save in `runAgent` goes through `persist()`, which sets `speaker` ("Rye" or "Marvin (@marvin)") on the assistant messages that turn added (`markSpeaker`). When earlier replies came from someone else, the turn's `<rye_context>` lists who wrote each and who is speaking now (`speakersNote`), so the model doesn't read another speaker's replies as its own. Save a session only through `persist()` inside `runAgent`.
- **Harness (`harness/claude-sdk.ts`, `llm-provider.ts`)**:
  - The `harness` setting (`"pi"` default, `"claude"`) picks what runs the model and takes precedence over `llm_provider` for the models it serves: with `harness = "claude"`, Claude model ids and blank model tiers run through the Claude Agent SDK.
  - The Claude harness is a pi-ai `ProviderStreams` implementation, so `agent/loop.ts` is unchanged: Rye's tools are bridged to the SDK as an in-process MCP server, and a live SDK session is continued by the last assistant message's `responseId`. Add future harnesses (e.g. opencode, hermes) the same way: a value in `HARNESSES`, a `ProviderStreams` module under `harness/`, and a provider registered in `llm-provider.ts`.
  - **Tool calls written as text** (`agent/text-tool-calls.ts`): some local models (Llama 3.1 in Ollama) write `{"name": …, "parameters": …}` instead of calling. A reply that is only such a call, to a tool the model was offered, is run as the real call; reply text that could still be one (starting with `{`, `[`, a ```json fence or `<|python_tag|>`) is held back while streaming and shown once it can't be.
  - Inject a fake `query` into `claudeAgentSdkApi` in tests; never start Claude Code from tests.
- **Tool Registration (`tools/index.ts`, `tools/groups.ts`)**:
  - Every new tool must be added to `TOOLS` + `executeTool` in `tools/index.ts` and assigned to a group in `STATIC_GROUPS` in `tools/groups.ts` (`core` is always loaded; other groups load via keyword/decision selector or `load_tools_tool`).
  - Run `bun test packages/agent-core/tests/tool-groups.test.ts` after adding or moving tools.
- **SQL databases (`db/connections.ts`, `db/drivers.ts`, `tools/sql.ts`)**:
  - Connections are named and per environment: `[databases.<name>]` (type `mysql` or `postgres`), changed or added to by `[environments.<env>.databases.<name>]` (`mergeDatabases`). The old `[mysql]` section is the connection named `mysql`. `listConnections` resolves them (URL, `password_env`, per-engine defaults) and sets misconfigured ones aside with a reason.
  - Three engine-neutral tools (`sql_query_tool`, `sql_schema_tool`, `sql_list_databases_tool`, group `sql`) take a `connection` name. The old `mysql_*` tool names and the old `mysql` group id are still answered (`LEGACY_MYSQL_TOOLS`, `GROUP_ALIASES`) because saved SOPs, skills and agents name them; don't offer them to the model again.
  - To add an engine: a `SqlDriver` in `db/drivers.ts`, its name in `DATABASE_TYPES`, and a read-only rule in `readOnlyViolation`. Postgres uses Bun's built-in client and runs every query in a server-enforced read-only transaction with a statement timeout; MySQL (mysql2) relies on the statement check and `KILL QUERY`, so that check also refuses an `EXPLAIN`/`DESCRIBE` of a write (MySQL's `EXPLAIN ANALYZE` runs the statement, and accepts `UPDATE`/`DELETE`).
  - **Keys.** `sql_schema_tool` with a table shows its indexes (primary, unique, partial, expression, method), its foreign keys and the foreign keys pointing at it (`SqlDriver.keys`, optional; `formatKeys`), so the agent joins along declared keys instead of guessing. Postgres reads them from the catalogs (`pg_index`, `pg_constraint`) like `describe`, since `information_schema` hides constraints from a SELECT-only user; MySQL from `information_schema.STATISTICS`/`KEY_COLUMN_USAGE`. A failure there leaves the columns and says why. `sql_query_tool`'s description tells the agent to check a possibly slow query with plain `EXPLAIN` first (it doesn't run the query; `EXPLAIN ANALYZE` does).
  - The agent is told connection names, engines, default databases and descriptions (in the environment block of the system prompt), never hosts or credentials. Tests swap the driver (`DriverLookup`); never connect to a real database from tests.
- **Vector index (`embeddings/vector-index.ts`)**: the one place vectors are compared. `VectorIndex` packs normalised vectors at one byte per dimension into a single array and scans it in a tight loop; `standsOut` judges a similarity against the query's background level, since raw cosine values mean different things per model. `KnowledgeStore` and `ChatStore` each build theirs lazily and drop it whenever their rows change. Don't add per-row cosine loops elsewhere.
- **Embeddings & Hybrid RAG (`embeddings/index.ts`, `knowledge/store.ts`)**:
  - `embedBatch` / `embedText` tries Ollama first (`/api/embed` with `/api/embeddings` fallback), then GitHub Copilot `/embeddings` if configured, and returns `null` cleanly if unavailable.
  - `KnowledgeStore` (`knowledge.db`) chunks Markdown by heading and combines SQLite `FTS5` BM25 with float32 cosine similarity using Reciprocal Rank Fusion (RRF), degrading cleanly to keyword-only FTS5 when offline.
- **Reranking (`embeddings/rerank.ts`)**: optional, chosen by `rerank.provider` (`[rerank]` in config, or Settings → Search): `decision` asks the decision model one yes/no question per note in a single request; `ollama` asks a chat model per note and scores the probability of "yes" on its first token (`logprobs`; Qwen3-Reranker builds get their own raw prompt); `server` posts to a `/v1/rerank` server. Ollama has no rerank endpoint and reports only the 20 likeliest tokens, so zerank (scored by one token's raw logit) and cross-encoders (bge-reranker) only work through `server` (`ollamaRerankProblem` says so in the UI). `KnowledgeStore.search` reorders a pool of `RERANK_POOL` candidates by it; `searchForContext` attaches only notes scoring `RELEVANT_SCORE` or more, in place of the similarity gate. Any failure or timeout returns `null` and search carries on unranked. Tests pass their own `rerank` function to `KnowledgeStore`; only the real knowledge base asks Ollama by default.
- **Changing the embedding model (`embeddings/models.ts`, Settings → Search)**: `PUT /models/settings {embedding_model}` first asks Ollama to embed one word with the model (`probeEmbeddingModel`; a model that can't load is refused, not saved), then reindexes in the background (`startReindex`, progress in `retrieval.embedding.reindex`). Vectors are only ever compared with a query embedded by the same model (`vectorIndex(dimensions, model)`). **The previous model's vectors are kept, one previous model at a time**: knowledge chunks in `knowledge_embedding_backup` keyed by model + hash of the embedded text (so `indexDoc` reuses any vector whose text and model are unchanged and restores from the backup instead of embedding), chat messages in `message_vectors_prev` (`ChatStore.useEmbeddingModel` swaps the two tables). Models that want an instruction before a query get it from `queryPrefix` (queries only, never documents), so embed queries with `embedQuery`/`embedQueryLocal`, not `embedText`.
- **Memory (`memory/store.ts`)**:
  - Entries are shown newest first up to `context.memory_budget_tokens`; the rest are listed by key only.
  - `memory.db` holds always-in-prompt entries (`kind: "fact" | "acronym" | "term"`, optional `agent_id`). Acronyms and terms render as a dedicated **Glossary & Acronyms** table in the prompt; facts render grouped by category.
- **Chat history (`chat/store.ts`)**:
  - `chats.db` (SQLite): one row per chat and one per message, so a save writes only the messages whose hash changed; message text is indexed with FTS5. **No chat is ever dropped for age** (there used to be a 50-chat cap, in the store and in the web app). Only `remove` deletes; `upsertMany` leaves chats it wasn't given alone.
  - The web app deletes on the server any chat missing from its in-memory list (`App.tsx` sync effect), so never filter or trim that list.
  - **Lazy loading.** The web app lists chats with `GET /chat/history?summary=1` (no messages) and fetches one chat's messages with `GET /chat/history/:id` when it is opened. A chat whose messages aren't loaded is `partial` (`utils/types.ts`). Three rules keep that from erasing history, and each has its own guard: a partial chat is saved without a `messages` key (`chatSaveBody`; the server's `upsert` then keeps its stored messages), it can't be sent into (`sendMessage`), and a run's messages are never written over it (`upsertChat`). A chat changed by another tab becomes partial again and is re-fetched if it is on screen.
  - `migrateLegacyChats` imports the old `chats.json` when the store opens: read-only on the file (it stays as a backup), one transaction, verified before commit, merge-only, remembered by file size + mtime. Don't weaken any of those.
  - `bun --watch` reloads the server on save, so a change to this store runs against the developer's real data directory immediately. Keep schema changes additive.
- **Message embeddings (`chat/store.ts`)**: `message_vectors` holds one vector per message (derived data, safe to delete). They are filled in the background a few seconds after saving goes quiet, **with the local model only** (`embedBatchLocal`; chat history is never sent to a hosted embedder), dropped by trigger when a message's text changes, and replaced wholesale when the embedding model changes. Tests must pass their own embedders as the third `ChatStore` argument; nothing but the real data directory's store embeds by default.
- **Conversation search (`chat/search.ts`, `tools/chats.ts`)**:
  - `ChatStore.search` is async and merges two searches: by words (below), then by meaning (messages whose vector stands out for the query; thresholds `RELATED_*` were tuned on `nomic-embed-text`). Chats containing the words always come first; chats found by meaning alone follow with `related: true`.
  - A chat needs most of the query's terms, not all (`requiredTerms`), with at least one non-filler term among those it has; what it lacks is returned in `missing`. Final order is: every term, then found by meaning, then partial. Messages under 30 characters are never offered as "related" (off-topic queries land closest to them).
  - Word search is fuzzy in two ways. Word forms: the FTS index stores word roots (`tokenize='porter unicode61'`) and `searchChats` compares a light `stem()`, so "lagging" and "lag" find each other. Typos: when a term matches nothing, `corrections()` looks in the `words` vocabulary for spellings within `typoBudget` edits and searches for those; a match reports the text it actually hit in `matched` so the UI can highlight it. Quoted phrases stay exact.
  - `rebuildSearchIndex` recreates the text index and vocabulary from the stored messages (read-only on chats and messages, one transaction). It runs when `meta.search_index` differs from `SEARCH_INDEX_VERSION`; bump that constant to change how text is indexed.
  - `ChatStore.search` uses the FTS index (word-start matching, with a `LIKE` scan only when a term matches nothing) to find chats containing every term, then `searchChats` ranks and excerpts the newest 300 of them (case-insensitive substring; quoted phrases stay whole). `GET /chat/search?q=` serves the search dialog; `search_chats_tool` and `read_chat_tool` (tool group `chats`, loaded when the user refers to an earlier conversation) serve the agent.
- **Custom Agents & Routing (`agents/store.ts`, `agents/router.ts`, `agents/settings.ts`)**:
  - `agents.db` stores custom agents (`id`, unique `slug`, `name`, `description`, `instructions`, `avatar`, `model`, `env`, `tool_groups`).
  - Profile images up to 400 KB are embedded in `avatar.value` as a data URI; larger ones (up to 8 MB) are uploaded with `POST /agents/avatars`, stored under `agent-avatars/` in the data dir, and referenced by URL (`agents/avatars.ts`).
  - Dedicated agent chats set `agentId` on `ChatHistoryRecord` (`chats.db`). An empty agent chat (e.g. picking an agent from the model picker on a new chat) greets with the agent's picture in the orb's place (`ChatHero`'s `agent`, `AgentAvatar` size `hero`, 78px) and "You're chatting with …".
  - In generic chats, explicit `@slug` mentions route that turn directly; optional decision-model auto-routing (`autoRoute`) and agent-to-agent follow-up hops (`allowAgentReplies` + `chattiness`) are stored in `agent-settings.json` and stream follow-up replies via `agent_turn_start` SSE events.
  - **Tags hand over.** With `allowAgentReplies` on, every agent (and Rye) is told the other agents' tags in its system prompt (`teammates` argument of `runAgent`), and an agent tagged in a reply answers next, ahead of the decision model's pick (`pickTaggedAgent`); a second agent the user tagged also gets its turn. Tag hand-offs always get at least one hop, even with chattiness `off`. Replies draw `@slug` as an agent pill (`remarkAgentMentions` in `MessageList.tsx`).
  - **Every `/chat/` stream ends with `done` or `error`.** The web app only saves a run on `done`, `error` or `prompt`.
    - **The bug this prevents:** with agent replies on, a first turn that stopped early (the tool-round pause, an ask_user question) used to close without `done`. The reply blanked out, Continue never showed, and the chat wasn't saved.
    - **Where it's enforced:** turn sequencing lives in `agents/turns.ts` (`runTurns`, `TurnOutcome.ended`), tested in `tests/chat-turns.test.ts`.
    - **Backstop:** if a stream still closes without either (a server restart mid-run), `sendMessage` saves what streamed (`streamEnded`).
  - **Authoring chats are not agent chats.** A `/chat/` request with `system_prompt_suffix` (the AI create/edit chats for SOPs, Skills and Agents) is never routed to an agent, by tag, auto-routing or follow-up, and runs on the `extraction` task model ("SOP & Skill capture" in Settings) unless the request names a model.
  - **Quick chat requests (`quick: true`).** The web app's quick chat: the user's own `@slug` tags route the turn as usual, but there is no auto-routing and no follow-up hops; it runs on the low model tier (`resolveTierModelId(…, "low")`) unless the request names a model or a tagged agent has its own. Decided by `chatRequestKind` (`agents/turns.ts`, tested in `tests/chat-turns.test.ts`). The quick chat isn't stored, so its edit/retry `rewind` is `{index, messages}` (its own messages; only the session is cut) instead of `{chat_id, index}` (`chat/rewind.ts`).
- **Code sessions (`code/`, design and contract in `docs/design/code-sessions.md`, `code/types.ts`, `packages/shared/src/code.ts`)**: a code chat (`chats.kind = "code"`) runs a coding agent in a sandboxed, Rye-owned clone of an allowed repo, on a branch of its own.
  - **Off until configured.** On means `[code] enabled` and at least one `[[code.repos]]` (`codeSessionsEnabled`, `code/service.ts`; being in `code_search.repos` does not count). Off, every `/code/` route answers a JSON 404 (`/code/engines` included, which keeps the web UI hidden), the `code` tools aren't in `getTools()`, and `code.db` is never opened. Keep it that way: a Rye without `[code]` must behave exactly as before.
  - **Modules.** `policy.ts` (`commandVerdict`/`pathVerdict`), `sandbox.ts` (the OS sandbox plan, scrubbed env, git shim), `workspace.ts` (clone, snapshots `refs/rye/<id>/turn-<n>`, archive/restore; `session.json` is `{version: 1, workspace}`), `git.ts` (the hardened git runner, diffs, create-only branches, `merge-tree`), `engine.ts` + `engines/claude.ts` (the Agent SDK engine), `engines/acp.ts` + `acp/` + `engines/copilot.ts` (below), `process-sandbox.ts` (the whole-process sandbox), `store.ts` (`code.db`: additive, versioned schema; add columns to `COLUMNS`, never drop), `runner.ts` (runs), `routes.ts` (`/code/`, mounted with a trailing slash), `service.ts` (the process's lazily built runner), `naming.ts` (below).
  - **Naming a new session (`code/naming.ts`).** `CodeRunner.create` asks the "Titles & step labels" model for a title (`nameSession` dep → `suggestTitle` in `agent/loop.ts`, the helper `generateChatTitle` uses, with the repo as context), started alongside the sandbox and engine checks and given up on after `NAME_TIMEOUT_MS` (4 s, request aborted). `cleanAiTitle` makes it sentence case, ≤ 6 words; without it the title is `fallbackTitle`: `<repo>: <the task's meaningful words>`. A `title` in the request wins and the model isn't asked. The branch is `rye/<branchSlug(title)>-<4 chars of the id>`: lowercase, at most four words, `FILLER_WORDS` (let's, see, what, please, add, additional, the, …) and the repo's name dropped, `session` when nothing is left; `SLUG_RE` and create-only refs still apply. Existing sessions keep their titles and branches. Tests inject `nameSession`; none of them reaches a model.
  - **Runs are detached** (`CodeRunner`): no request owns a run; closing a tab never stops it. Every event is appended to `<session>/events.jsonl` with an increasing `seq` in the chat's `SSEEvent` vocabulary; `/events?after=<seq>` replays strictly after it, then follows (frames `id: <seq>` + `data:`). A turn opens at its first event (`iter_start`) and closes with `done`/`error`, so the view pairs the n-th user message with the n-th turn; a message sent mid-run steers it (`CodeRun.send`) and logs its own turn boundary. **The server owns a code chat's messages**: it stores each user message when its turn starts (`ChatStore.appendMessage`), client saves never replace them, and the web app saves code chats without `messages`.
  - **Approvals are live prompts** (`prompt` with `live: true`, options exactly `Allow once` / `Allow "<pattern>" for this session` / `Deny`, the question written by Rye from the parsed request, never the agent's prose), answered at `/approvals/:promptId` (409 `answered` once settled), denied after `approval_timeout_minutes`. A session approval is stored and replayed into later runs (`allowForSession(pattern, hosts)`). `max_turns`/`max_cost_usd` ask to continue (Continue / Stop). Every state change appends `code_status`.
  - **This machine is off limits.** Rye's API is unauthenticated on localhost, so an agent that reaches it could answer its own approvals. A real run proved this happened while the sandbox had `allowLocalBinding: true`. Keep all three guards:
    - the sandbox plan has `allowLocalBinding: false`;
    - `isLocalHost` (localhost, loopback, private, link-local and metadata addresses, `.local`/`.internal`) makes every network command to such a host a deny that can't be approved or allow-listed, and approved hosts are filtered through it (`allowForSession`, `withApprovedHosts`);
    - WebFetch, which runs outside the sandbox, refuses local hosts.

    Test any sandbox change with a real localhost probe.
  - **Safety rules.** Every `/code/` write route takes JSON from a local origin only (`refuseForeignWrite`). Stage, discard, Create branch, Merge, archive, restore and delete answer `busy` while a run is going. Rye writes in the user's repo only objects, `refs/rye/<id>/*` and **new** `rye/*` branches (create-only); branches the user keeps carry the user's `user.name`/`user.email` (read as plain files, `userGitIdentity`), snapshots carry Rye's. Deleting a code chat archives its session (`ChatStore.onRemoveKind` → `chat/kinds.ts`), never deleting work; only `DELETE /code/sessions/:id` (Settings → Code) removes a workspace and its refs. After a restart `recover()` closes a cut-off turn; the next message resumes the engine session.
  - **A base with no commits yet** (HEAD names a branch that doesn't exist, as after `git init`): `workspace.create` writes one empty root commit (Rye's identity) to the user's objects, pins it as `refs/rye/<id>/base` and clones from it (`Workspace.baseUnborn`, `emptyRootSha`; `includeUncommitted` carries only staged files, untracked never). While the base is unborn, status compares with the pinned base (`BranchStatus.baseUnborn`) and Merge is refused ("use Create branch"); once the user commits, status counts against the real tip without Rye's root, and Merge uses `merge-tree --allow-unrelated-histories` onto a new branch. `/code/repos` (`unborn`) and the branches route (`unbornBranch`) say so, and the New code session dialog notes it. A base naming nothing else gets `missingBaseMessage` (the branches that exist).
  - **Chat kinds (`chat/kinds.ts`).** `chats.kind` and `chats.parent_chat_id` are server-owned like the folder fields (added by `ALTER TABLE` behind `PRAGMA table_info`; set only by `createKindChat`). `POST /chat/` hands a request to `kindChatTurn` first, which answers only for a `chat_id` whose stored kind has a registered `ChatKindServer`; every other request takes the unchanged chat path.
  - **Tools (`tools/code.ts`, group `code`).** `start_code_session_tool` only proposes: the loop shows Start / Cancel at the end of the turn and the next message decides (like `add_mcp_server_tool`); a started session appears in the parent chat as a tool result carrying `[rye:code-session:<id>]` (the card). `code_session_status_tool` is read-only.
  - **ACP engines (`acp:<cli>`; `acp:copilot` is the GitHub Copilot CLI, `[code] copilot_path`).** `engines/acp.ts` drives any Agent Client Protocol CLI described by an `AcpAgentProfile` (command and flags, env allowlist, its own files, its API hosts, availability from files only). Its `ownSandbox` is false, so the **whole CLI process** runs in `@anthropic-ai/sandbox-runtime` (`process-sandbox.ts`), and the engine refuses to start without it. srt's configuration is process-wide, so each process brings its filesystem rules per call and its hosts as a per-command network list (updated after approvals). Keep local binding off, or the agent could reach Rye's API. `session/request_permission` goes through `judgeAcpToolCall` (the Claude engine's rules). Rye answers `allow_once`/`reject_once`, never `allow_always`. It offers `fs/*` only when the profile asks (through `pathVerdict`) and never `terminal/*`. The CLI is kept between a session's turns (Copilot can't load another process's sessions). Copilot's env is `copilotEnv()` (`harness/env.ts`): only `COPILOT_GITHUB_TOKEN` as a token, never `GH_TOKEN`/`GITHUB_TOKEN`. To add an agent, write a profile and register it in `codeEngines()`.
  - **Testing.** Use `scriptedCodeEngine` (`code/engines/fake.ts`) and the helpers in `tests/code-test-utils.ts` (temporary repos and stores, injected timers for the approval timeout). **Never start Claude Code, `sandbox-exec`, bubblewrap, sandbox-runtime or any CLI agent**, in tests or anywhere else. ACP engines are tested against `tests/fixtures/fake-acp-agent.ts` through a stub `ProcessSandbox` (`tests/code-engine-acp.test.ts`). For a browser check, `RYE_CODE_FAKE_ENGINE=1` (test-only, ignored unless exactly `1`) replaces the `claude` engine with a scripted demo that edits files and asks one approval; run it only on a throwaway `RYE_DATA_DIR`/`RYE_CONFIG_DIR`.

### Persistent Data Locations

- Config: `~/.config/rye/config.toml` (override with `RYE_CONFIG_DIR`) + `.env`
- Runtime data (`~/.local/share/rye/`, override with `RYE_DATA_DIR`):
  - `chats.db` (plus `chats.json` from before the move to SQLite, kept as a backup), `chat-folders.json`
  - `memory.db`, `knowledge.db`, `agents.db`, `sops.db`, `usage.db`
  - `code.db` and `code/<session>/` (`repo/`, `tmp/`, `cache/`, `events.jsonl`, `session.json`), only once code sessions are used
  - `skills/<name>/SKILL.md`
  - `model-settings.json`, `agent-settings.json`, `user-profile.json`, `pricing.json`

### Frontend (`apps/web/src/`)

- **Shared Authoring Components (`components/authoring/`, `components/shared/`)**:
  - Use `CreateResourceModal` + `AiCreateChat` for create/edit modals (shared by SOPs, Skills, and Agents).
  - Use `AiEditorSheet` for slide-over AI Editor panels (shared by SOPs, Skills, and Agents).
  - Use `MarkdownEditor` for Markdown authoring (supports optional `mentions` for `@`/`#` reference tagging).
  - Use `AgentAvatar`, `AgentBanner` (static frame-0 canvas wash for images so GIFs don't animate in banners), `AgentHoverCard`, and `AgentMentionPill` / `AgentMentionText` for consistent agent identity.

- **AI mark orb (`components/chat/HeroMark.tsx`, `.hero-mark` in `styles/chat.css`)**: the spark above the empty-chat greeting (100px, 92px on phones) and in the authoring empty state (`AiEmptyState`, 52px) is light flowing inside a drop of glass, drawn by a WebGL1 shader. The user rejected discrete lobes of banded colour on orbits ("wobbly candy corn") and asked for something organic, fluid and refractive like glass, with the star in the centre: don't bring back separate shapes or bold tri-colour bands. **Not a sphere:** the outline is a circle bent by four slow low-frequency terms (`SHAPE_AMPS`, k = 1…4, each amplitude swelling and fading; about 4–7% of the radius, never lumpy), so it leans, stretches and swells like a droplet; the surface normal comes from that outline, so the lens and the reflections change as it morphs. **It must read as glass:** clear and darker than the background on a dark theme, pale and frosted on a light one (never grey; cool silver for graphite); a window's reflection at the upper left found by the reflected view ray (one soft pane with a faint mullion; it slides with the outline's lean, `sway`, and the pointer); Fresnel sheen of a dim room brightening the rim; the lens (`LENS`) pushing content out ever more steeply toward the rim, so the flow is squeezed against the edge; a thick spot (`uBlob`) magnifying what drifts under it; a caustic pooling at the lower inside (`uCaustic`); a thin spectral rim line. **The flow is one continuous field, like dye in water:** gradient-noise fbm domain-warped twice (`a`, then `b`), each layer's offset circling its own slow loop (`DRIFTS`, so coordinates stay small), turned slowly and by a swirl strongest in the middle that swings one way and back (`SWIRL`, never winding up); lit by `dye()` (a steep rise above a threshold plus a thin thread just below it) only where the first warp gathers it, coloured continuously between the accent, the AI accent and the accent turned toward magenta by the warp's own values, white only in the hottest cores (high dynamic range). The low frequency (`FREQ`) and 3 octaves are deliberate: more detail reads as marble or smoke. **Dispersion:** the final field is evaluated at three wavelengths (shifted along the lens and a small prism) and interpolated quadratically for each of `SAMPLES` = 7 wavelength samples; the spectral sum in linear light, minus the undispersed light, is a faint fringe on the edges of bright threads. The caustic, the rim line and the star's edge are spectral sums too (`waves`). Never per-channel RGB offsets. **The star sits in the middle, inside the glass:** the star and companion (`starField`/`starDist`, `SPARK_SHARE`) are lensed more than the flow, bent by the warp (`bend`), twisted a little by the swirl, their edges dispersed through the distance gradient; the flow dims a little round them and bright flow passing in front veils and tints the glow; a squeezed reflection slides round the inner rim. It is the brightest light and must stay recognisable at 52, 80 and 100px. Dark theme: light is added to the dark glass and tone mapped; light theme: it tints the frosted body by coverage, turns white where hottest, and the spark sits in a soft aura of its glow colour. The light theme must not look washed out against a white page (the user asked for this): its flow colours are `vivid`, coverage and tint depth are high and the tint slightly darkened (`tone`), the body and rim carry the accent, and the spark's glow is saturated. Check every change in light mode as well as dark, with several accents. Outside: a bloom lit by a two-lookup estimate of the flow at the rim, and a faint ring of dots following the outline (concentric rings, alternate ones turning the other way, each dot twinkling, spaced in CSS pixels). **Cost:** the flow is evaluated only inside the outline (outside pixels return after the bloom and dots); inside, about 95 transcendental ops plus 23 gradient-noise lookups per pixel (7 fbm calls × 3 octaves, 2 at the rim); in SwiftShader it draws slightly faster per canvas than the earlier glass version (about 165 transcendental ops everywhere). Four cores or fewer, or a phone-width window (`MOBILE_QUERY`), get the lighter path: 2 octaves, 5 samples and ≤1.5× DPR (`DETAIL.lite`, `LITE_DPR`). Don't add warp levels, octaves or per-sample field evaluations. The `AiMark` SVG is only the fallback and hides via `[data-live]`. Motion is slow; it breathes (`BREATH_SECONDS`), and hover speeds it up, deepens the lens and the shape's sway and leans the view toward the pointer. The outline is anti-aliased in the shader and written premultiplied to a transparent canvas (`premultipliedAlpha: true`); the canvas bleeds past the orb (`--hero-mark-bleed`) so the bloom, the sway and the dots have room, without affecting layout. Colours are read from `--main-accent`, `--main-accent-alt`, `--main-ai-accent`, `--main-bg` and `--main-fg` at draw time and re-read when `data-theme`/`data-accent` change on `<html>`. Phases and drifts are wrapped on the CPU so the GPU never sees a large value; keep under 64 fragment uniform vectors. It draws at ≤30 fps and ≤2× DPR, pauses when the tab is hidden or it is off screen, draws one still frame under reduced motion, and loses its context on unmount; the `.hero-mark::before` gradients (dark glass, pale on a light theme, clipped to a slightly irregular drop, `--hero-mark-shape`, with soft clouds of the accent and AI accent pooling low, a window's highlight at the upper left and a glow behind the SVG spark) plus the `::after` faint conic spectral rim (built from the `--accent-*` preset tokens) are the fallback without WebGL (faded out via `[data-live]` once the canvas draws). The caller's class (`chat-hero-mark`, `ai-empty-icon` 52px) sets its size; the spark scales with it.
